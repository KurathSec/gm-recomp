# 64-bit (x86-64) runners

GameMaker Studio 2's later Windows runners are 64-bit only: 7 of 10 sampled archive games.
This is how the runtime runs them alongside the 32-bit path. The 32-bit path is not changed:
its state hashes stay the same.

## Address space

Guest memory stays one 32-bit wasm memory, and a memory access uses the low 32 bits of
its 64-bit effective address. The GameMaker runners are fixed at 0x1_4000_0000 (their
relocations stripped), so the image is mapped where those low 32 bits point,
0x4000_0000, and nothing else may live there. The code keeps computing real 64-bit
addresses (RIP-relative operands and pointers in the image are 0x1_40xx_xxxx), so
pointers stay consistent with each other; only memory accesses and the dispatcher use
the low half. Everything the runtime allocates (heaps, stacks, `VirtualAlloc`, TEB/PEB,
HLE stubs) is below 4 GB, upper half zero. An API that hands out an address inside a
64-bit image (a module handle, `GetProcAddress` of its export) gives the full address
(`LoadedModule::base_high`). An image whose place below 4 GB is taken is relocated there
if it keeps relocations.

## Loading (crates/pe, runtime loader)

- PE32+ optional header (magic 0x20b): `ImageBase` and the stack/heap sizes are 64-bit,
  the data directories follow after 112 bytes instead of 96.
- Import thunks and the IAT are 8 bytes (ordinal flag in bit 63).
- Base relocations of type DIR64 (10) add the 64-bit delta (only when the image cannot
  stay at its base).
- TLS directory with 64-bit addresses; exception directory (`.pdata`: RUNTIME_FUNCTION
  begin/end/unwind RVAs) for unwinding.

## CPU (crates/x86 discovery, crates/recomp)

- Decoding and discovery at bitness 64: RIP-relative operands, 8-byte jump-table entries
  and RVA-relative tables (`jmp [base + idx*4]` + `add`).
- A function's registers are wasm parameters and results, as in 32-bit, but 16 i64
  (rax..r15). A 32-bit write zero-extends to 64 bits; 8- and 16-bit writes keep the
  rest; REX byte registers (spl, bpl, sil, dil, r8b..r15b).
- Flags as in 32-bit (lazy), with 64-bit operand widths.
- XMM0..15 (16 instead of 8). No x87 in practice (the Win64 ABI uses SSE).
- `call` pushes an 8-byte return address; `push`/`pop` move 8 bytes.
- `gs:` addresses the TEB (as `fs:` does in 32-bit).

## Windows ABI (runtime hle)

- Arguments in rcx, rdx, r8, r9, then on the stack from `rsp + 0x28` (after the return
  address and 32 bytes of shadow space); floating-point arguments in xmm0..3 by
  position; the result in rax (xmm0 for floats). The caller removes the arguments: no
  stdcall pops.
- `Ctx::arg(i)` reads by this convention when the process is 64-bit; callbacks into the
  guest (window procedures, DllMain, TLS callbacks, thread starts, COM from the guest)
  pass arguments the same way and reserve shadow space.
- Structures with pointers, handles or `SIZE_T` change layout. The APIs the 64-bit runner
  calls read and write them through pointer-size helpers; COM vtables have 8-byte entries.
- TEB64: self at 0x30, PEB at 0x60, stack base/limit at 0x08/0x10, TLS slots at 0x1480,
  last error at 0x68. PEB64: image base at 0x10, process heap at 0x30.

## Exceptions

x64 SEH is table-based (`hle/seh64.rs`, after Wine's ntdll): `RaiseException` and
faults walk the frames from the faulting context with each image's `.pdata` entries and
unwind codes, calling the language handlers that want exceptions; a handler that takes
one calls `RtlUnwindEx`, which calls the unwind handlers up to its frame and continues
there (C++ `catch` blocks through `STATUS_UNWIND_CONSOLIDATE`'s callback). The walk
goes on past a callback an API made (`Process::host_frames64`), and a context continued
above such a callback unwinds that host frame too. The 32-bit GameMaker Studio 2
runners raise no exceptions in normal play, so this has not met a real one yet.

## Other differences

- x87 instructions still appear in 64-bit code (setjmp's control word, the odd `long
  double` routine): they run through the 32-bit path's helper.
- A process loads images of its own bitness only: games ship 32-bit extension DLLs that
  their 64-bit runner cannot load, and LoadLibrary fails for them as on Windows
  (ERROR_BAD_EXE_FORMAT).
- A Direct3D 11 frame shorter than half a display frame (a game speed such as 9999, a
  runner that does not wait) takes a display frame of virtual time, as vsync would give
  it, so `delta_time` follows what the player sees.
